> [!summary] 한 줄
> 셋 다 「브라우저가 서버에 요청하고 응답받는 규칙」이고 URL·헤더·상태코드는 같다. 다른 건 **그 요청들을 어떻게 한 줄기(연결)에 실어 보내느냐**. 1.1 = 연결 하나에 요청 하나씩 → 브라우저가 주소당 연결을 6개까지만 열어 7번째부터 줄을 선다. 2 = 연결 하나에 여러 요청을 섞어 보낸다(그래서 6개 한계가 없다). 3 = 2 와 같은 생각을 TCP 대신 **UDP 위에 새로 만든 QUIC** 로 — 패킷 하나 잃어도 다른 요청이 안 멈추고, 와이파이↔LTE 가 바뀌어도 연결이 살아남는다.

## 1. 세 버전을 한 그림으로
```
HTTP/1.1   브라우저 ══연결1══ 요청A → 응답A → 요청B → 응답B …   (연결 6개까지 나란히, 7번째는 대기 = Stalled)
HTTP/2     브라우저 ══연결1══ [A1][B1][C1][A2][B2][C2] …          (한 연결에 조각(프레임)을 섞어 보냄 = 멀티플렉싱)
HTTP/3     브라우저 ~~QUIC(UDP)~~ [A1][B1][C1] …                   (같은 멀티플렉싱, 단 TCP 가 아니라 QUIC)
```

| | HTTP/1.1 (1997) | HTTP/2 (2015) | HTTP/3 (2022) |
|---|---|---|---|
| 아래 층 | TCP | TCP | **QUIC** (UDP 위에 만든 새 전송 규칙) |
| 연결 하나에 | 요청 1개씩 순서대로 | 여러 요청 동시에(스트림) | 여러 요청 동시에(스트림) |
| 브라우저 연결 수 | 주소당 6개 | 1개 | 1개 |
| 패킷 하나 잃으면 | 그 연결만 멈춤 | **연결 전체가 멈춤**(TCP 가 순서를 맞추느라 뒤 데이터를 안 줌 = TCP head-of-line blocking) | 잃은 스트림만 멈춤 |
| 연결 맺기 | TCP 1왕복 + TLS 1~2왕복 | 같음 | TLS 1.3 이 QUIC 안에 들어 있어 1왕복, 다시 접속은 0왕복 |
| 암호화 | 선택(https 면) | 사실상 필수(브라우저가 https 에서만 씀) | 필수(TLS 1.3 내장) |
| 네트워크 바뀔 때(와이파이→LTE) | 연결 끊김 | 끊김 | **연결 ID 로 이어감(connection migration)** |
| 헤더 | 매번 글자 그대로 | HPACK 압축 | QPACK 압축 |

> [!example] 1.1 의 「6개 한계」가 체감되는 경우
> 지도·이미지 타일처럼 한 화면에서 작은 파일 수십 개를 한꺼번에 받으면, 7번째 요청부터 DevTools 에 **Stalled** 가 길게 찍힌다. 프록시에서 HTTP/2 를 켜면 연결 하나에 다 섞여 이 대기가 사라진다.

## 2. 왜 HTTP/3 는 UDP 위에 새로 만들었나
- TCP 는 **운영체제 커널**이 구현한다. 수십 년 된 규칙을 고치려면 모든 OS·공유기·방화벽이 바뀌어야 해서 사실상 못 고친다(「ossification」).
- UDP 는 「보내면 끝」인 가장 단순한 규칙이라 아무 장비나 통과시킨다. 그 위에 **브라우저와 서버 프로그램 자신이** 순서·재전송·혼잡 제어·암호화를 구현한 것이 QUIC 이다. 그래서 OS 를 안 바꿔도 새 기능(스트림 독립·0-RTT·연결 이주)을 넣을 수 있었다.
- 대가: 암호화·재전송을 커널이 아니라 프로그램이 하므로 **CPU 를 더 쓴다**(같은 트래픽에 1.5~2배라는 측정이 흔함). 서버 프로그램(nginx 등)이 QUIC 코드를 **갖고 있어야** 한다 — 아래 「켜는 법」의 첫 조건.

## 3. 서버에서 켜려면 — 「QUIC 포함 빌드 · UDP 443 · Alt-Svc」
### (1) nginx 가 QUIC 을 포함해 빌드돼 있어야 한다
- HTTP/2 는 nginx 가 오래전부터 기본으로 갖고 있어 `http2 on;` 한 줄이면 된다. Nginx Proxy Manager(NPM)의 「HTTP/2 Support」 체크가 이 줄을 넣는다.
- HTTP/3 는 nginx **1.25 이상**을 `--with-http_v3_module` 로 컴파일해야 하고, TLS 라이브러리도 QUIC 을 아는 것(OpenSSL 3.5+, BoringSSL, quictls)이어야 한다. 배포판 패키지·도커 이미지 상당수가 아직 이 옵션 없이 만들어져 있다.
- 확인: `nginx -V 2>&1 | grep -o with-http_v3_module`
- NPM 처럼 관리 화면이 붙은 프록시 이미지는 QUIC 모듈 없이 빌드돼 있고 화면에 HTTP/3 스위치가 없는 경우가 많다. 켜려면 이미지를 직접 만들거나, 앞에 Caddy/Traefik 처럼 QUIC 이 되는 프록시를 하나 더 둔다.

### (2) 방화벽에 UDP 443 을 열어야 한다
- 포트 번호는 같아도 **TCP 443 과 UDP 443 은 다른 문**이다. 방화벽 규칙은 「프로토콜 + 포트」 단위라, `ufw allow 443/tcp` 만 있으면 QUIC 패킷은 버려진다.
- HTTP/3 를 하려면 `ufw allow 443/udp` 가 따로 필요하다. 클라우드·호스팅 쪽 방화벽(보안 그룹)이 따로 있으면 거기도 연다.
- 회사 방화벽·일부 공유기는 UDP 443 을 막는다. 그래서 HTTP/3 는 항상 **TCP 로 되돌아갈 길(폴백)** 을 둔다 — 그 장치가 (3).

### (3) Alt-Svc 헤더로 「HTTP/3 도 있다」고 알려야 한다
- 브라우저는 처음엔 **TCP 로** 접속한다(UDP 가 될지 모르니까). 서버가 그 TCP 응답에 이런 헤더를 실어 보낸다:
  `Alt-Svc: h3=":443"; ma=86400` — 「같은 호스트의 UDP 443 에 h3 가 있다, 하루(86400초) 동안 기억해라」.
- 브라우저는 다음 접속부터 QUIC 으로 시도하고, 안 되면 TCP 로 돌아간다. 즉 HTTP/3 는 **두 번째 접속부터** 켜진다. (DNS 의 `HTTPS` 레코드로 처음부터 알리는 방법도 있다.)
- nginx 설정 예:
  ```nginx
  server {
    listen 443 quic reuseport;     # UDP 443 = HTTP/3
    listen 443 ssl;                # TCP 443 = HTTP/1.1·2
    http2 on;
    ssl_protocols TLSv1.3;
    add_header Alt-Svc 'h3=":443"; ma=86400';
  }
  ```

## 4. 리버스 프록시 뒤에서는 어디에 적용되나
```
브라우저 ──(여기만 1.1/2/3 선택)──▶ 리버스 프록시(TLS 종료) ──HTTP/1.1──▶ 백엔드 앱
```
- 버전은 **브라우저↔프록시** 한 구간에만 적용된다. 프록시 뒤쪽(`proxy_http_version 1.1`)은 그대로다. 백엔드 앞에 [[SSH 터널 — -L·-R·ProxyJump|SSH 터널]]이 있어도 마찬가지다.
- 그래서 HTTP/2 를 켠다고 백엔드가 바뀌는 건 없다. 브라우저의 연결 6개 한계만 사라진다.
- HTTP/3 의 추가 이득(패킷 유실·네트워크 이동)은 유선·안정된 와이파이에서 큰 응답을 받는 패턴에선 작다. 모바일 사용자가 많거나 「연결이 조용히 끊겨 오래 멈춤」이 반복되면 그때 QUIC 의 빠른 재연결·이주가 후보가 된다.

## 5. 확인하는 법
- 크롬 DevTools → Network → 열 머리에서 우클릭 → **Protocol** 열: `http/1.1` · `h2` · `h3`.
- `curl -sI --http2 https://api.example.com` / `curl -sI --http3 https://api.example.com`
  - curl 이 해당 기능을 넣어 빌드돼 있어야 한다. `curl -V` 의 Features 에 `HTTP2`·`HTTP3` 가 있는지 본다. Windows 기본·git-bash curl 은 빠져 있는 경우가 있다.
- 외부 검사: https://http3check.net , https://tools.keycdn.com/http2-test

## 6. 함정 모음
- HTTP/2 는 연결이 하나라 **그 연결이 죽으면 전부 죽는다** — 크롬은 재사용 전에 PING 으로 살았는지 확인해 1.1 보다 빨리 알아챈다.
- UDP 는 공유기 NAT 의 기억 시간이 짧다(30초 안팎). QUIC 은 PING 프레임으로 유지하지만, 오래 쉰 뒤 첫 요청이 느릴 수 있다.
- 리버스 프록시가 HTTP/2 를 받아도 뒤쪽은 1.1 인 게 보통이다. 뒤쪽 서버의 동시 처리 한계(스레드 수 등)는 그대로다.
- `Alt-Svc` 는 **응답 헤더**다 — 프록시가 헤더를 지우거나 캐시가 끼면 h3 로 못 올라간다.
