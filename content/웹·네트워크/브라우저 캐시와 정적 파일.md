계기: 관리자 화면 로그인 배경사진(약 600 KB)을 보고 나온 질문. 「배경사진은 서버에서 받아와? 정적으로 넣으면 안 돼? 접속할 때마다 받아오는 거야?」, 「그게 파일 경로에서 생기는 차이야?」

## 한 줄 답
- 배경사진은 처음부터 **정적 파일**이었다. API·DB가 아니라 화면 파일과 같은 웹서버(nginx)가 보내는 고정 파일이다.
- 처음 접속하면 어떤 방식이든 한 번은 내려받는다. 그림이 보이려면 브라우저가 그 파일을 받아야 한다.
- 차이는 **다시 접속할 때** 생긴다. 폴더에 따라 파일 이름과 주소가 달라지고, 웹서버는 주소에 따라 캐시 규칙을 다르게 붙인다.

## 개념 1 — 정적 파일과 동적 응답
| | 정적 파일 | 동적 응답 |
|---|---|---|
| 예 | JS·CSS·그림·글꼴 | `/api/v1/items` 목록 |
| 누가 만드나 | 빌드할 때 한 번 만들어 둔 파일 | 요청마다 서버 코드가 DB를 읽어 만듦 |
| 보내는 쪽 | 프런트엔드를 서빙하는 nginx | API 서버(예: FastAPI) |

「서버에서 받아온다」는 말이 둘 다에 쓰여서 헷갈린다. 정적 파일도 어딘가의 서버가 보내지만, 계산 없이 디스크에 있는 파일을 그대로 보낼 뿐이다.

## 개념 2 — 브라우저 캐시와 재검증
브라우저는 받은 파일을 자기 디스크에 저장해 둔다(캐시). 다음에 같은 주소가 필요할 때 할 수 있는 행동은 셋이다.

| 행동 | 언제 | 네트워크 |
|---|---|---|
| ① 그냥 씀 | 서버가 「N일 동안 그대로 써도 된다」(`Cache-Control: max-age`, `immutable`)고 했을 때 | 요청 없음 |
| ② 물어보고 씀(재검증) | 기간 표시가 없거나 「매번 확인하라」(`no-cache`)고 했을 때 | 「바뀌었어?」 요청 한 번(`If-None-Match: <ETag>`). 안 바뀌었으면 서버가 본문 없이 **304 Not Modified**로 답함 |
| ③ 다시 받음 | 캐시에 없거나 바뀌었을 때 | 파일 전체 |

- **ETag** = 파일 내용의 지문. 서버가 파일과 함께 보내고, 브라우저는 다음에 이 지문을 들고 「아직 이거 맞아?」 하고 묻는다.
- 그러니 기간 표시가 없는 파일도 **통째로 다시 받지는 않는다.** 다만 접속할 때마다 ②의 짧은 확인 요청이 하나 나간다.

## 개념 3 — 왜 아무 파일에나 「30일 그냥 써」를 붙이지 않나
「그냥 써」를 붙이면 그 기간 동안 브라우저는 서버에 묻지 않는다. 그 사이 파일을 바꿔도 **이름이 같으면 사용자는 옛 파일을 계속 본다.**
해결은 **내용이 바뀌면 이름도 바뀌게** 하는 것이다(캐시 무효화, cache busting). 이름에 내용 지문(해시)을 붙이면 된다.

```
login-bg-Bb3kr7wq.webp   ← 사진을 바꾸면 Bb3kr7wq 부분이 바뀜 → 새 주소 → 브라우저가 새로 받음
```

이름이 곧 내용이니 같은 이름의 파일은 영원히 같다. 그래서 이런 파일에만 「30일 묻지 말고 써」(`immutable`)를 붙여도 안전하다.

## 개념 4 — Vite의 두 폴더
| 둔 곳 | 빌드가 하는 일 | 빌드 후 주소 | 코드에서 부르는 법 |
|---|---|---|---|
| `public/` | 손대지 않고 그대로 복사 | `/login-bg.webp` (이름 그대로) | 절대 경로 문자열 `'/login-bg.webp'` |
| `src/assets/` 등 코드 옆 | 코드에서 쓰는 파일만 골라 이름에 해시를 붙여 `/assets/`에 넣음. 아주 작은 파일(4 KB 미만)은 코드 안에 글자로 박음 | `/assets/login-bg-Bb3kr7wq.webp` | 상대 경로 `url('../assets/login-bg.webp')` 또는 `import` |

`public/`이 맞는 경우: 이름이 바뀌면 안 되는 파일(`favicon.ico`, `robots.txt`, 외부에서 주소로 가리키는 로고), 코드에서 부르지 않는 파일.

## 개념 5 — 웹서버가 주소마다 다른 규칙 (nginx 예)
```nginx
location /assets/ {                 # 해시 이름 파일들
    expires 30d;
    add_header Cache-Control "public, immutable";
}
location = /index.html {            # 화면의 시작 파일 — 늘 확인 (배포하면 새 해시 이름을 가리켜야 하니까)
    add_header Cache-Control "no-cache, must-revalidate";
}
location / { try_files $uri $uri/ /index.html; }   # 나머지(public에서 온 파일 포함): 기간 표시 없음 → 브라우저가 재검증
```

`index.html`은 매번 확인한다. 그래야 배포 직후 새 JS·CSS·그림의 해시 주소를 바로 알게 된다. 그 밖의 해시 파일은 30일 동안 묻지 않는다. 이 둘이 짝을 이뤄 「빠른데 옛 화면이 안 남는」 구조가 된다.

## 예: 배경사진을 `public/`에서 `src/assets/`로 옮기면
| | 전 | 후 |
|---|---|---|
| 파일 위치 | `public/login-bg.webp` | `src/assets/login-bg.webp` |
| CSS | `url('/login-bg.webp')` | `url('../assets/login-bg.webp')` |
| 빌드 후 주소 | `/login-bg.webp` | `/assets/login-bg-Bb3kr7wq.webp` |
| 응답 헤더 | ETag·Last-Modified만 | `Cache-Control: max-age=2592000` + `public, immutable` |
| 다시 접속 | 확인 요청 1번(304) | 요청 없음 |
| 사진 교체 | 같은 이름이라 옛 사진이 남을 수 있음 | 이름이 바뀌어 바로 새 사진 |

확인 명령:
```bash
curl -sI https://example.com/assets/login-bg-Bb3kr7wq.webp | grep -i cache-control
```

## 헷갈리기 쉬운 것
- **정적 ≠ 안 받음.** 정적은 「계산 없이 고정 파일을 보냄」이다. 첫 접속에는 받는다.
- **재검증 ≠ 다시 받기.** 304는 본문이 없는 짧은 답이다. 다만 요청 한 번의 왕복 시간은 든다.
- **사진을 코드 안에 글자로 박는 방법(base64 인라인)**도 있다. 하지만 수백 KB 사진이면 JS·CSS가 그만큼(+33%) 커지고, 로그인과 상관없는 화면도 그 무게를 진다. 작은 아이콘에만 쓴다(Vite는 4 KB 미만을 자동으로 이렇게 한다).
- **작은 파일은 `public/`에 둬도 괜찮다.** 매번 재검증하지만 304 한 번이라 부담이 작다.
